# รายงานสรุปภาพรวมและสถาปัตยกรรม — I-Tech ระบบรับชำระเงินภาคสนาม

> เอกสารนี้อธิบายภาพรวมและการตัดสินใจเชิงวิศวกรรมของระบบ เพื่อใช้อ้างอิงและเผยแพร่ต่อสาธารณะ โดยไม่เปิดเผยซอร์สโค้ด โครงสร้างตารางของฐานข้อมูลองค์กร ข้อมูลลูกค้า ที่อยู่ของระบบ หรือค่าตั้งค่าใดๆ

## 1. ภาพรวม

I-Tech เป็นระบบสำหรับงานรับชำระเงินภาคสนาม เจ้าหน้าที่ออกไปพบลูกค้า บันทึกการรับเงิน แนบหลักฐาน และออกเอกสารได้จากหน้างาน โดยข้อมูลเชื่อมกลับเข้าฐานข้อมูลขององค์กรที่ใช้งานอยู่เดิม

พัฒนาช่วง **กรกฎาคม 2023 ถึง กันยายน 2024** ร่วมกับทีมของผู้ว่าจ้างรวม 4 คน

| ส่วน | เทคโนโลยี |
|---|---|
| หน้าเว็บ | Nuxt 2, Vue 2, Vuetify, Vuex |
| API | Node.js, Express, Sequelize |
| ฐานข้อมูล | Microsoft SQL Server (ของเดิมขององค์กร) |

## 2. ข้อจำกัดที่กำหนดรูปร่างของระบบ

โจทย์นี้ไม่ใช่การเริ่มจากศูนย์ แต่เป็นการสร้างระบบใหม่บนฐานข้อมูลที่มีอยู่ก่อนและเปลี่ยนโครงสร้างตามใจไม่ได้ เพราะมีระบบอื่นขององค์กรใช้ข้อมูลชุดเดียวกันอยู่

หลักที่ยึดคือ **ระบบใหม่ปรับตัวเข้าหาของเดิม ไม่ใช่ให้ของเดิมปรับตาม** ซึ่งต่างจากโปรเจกต์ที่ออกแบบฐานข้อมูลเองได้ตั้งแต่ต้น และเป็นข้อจำกัดที่ส่งผลต่อทุกการตัดสินใจหลังจากนั้น

## 3. เลขที่เอกสารต้องไม่ซ้ำและไม่ข้าม

เอกสารทางการเงินต้องมีเลขที่เรียงลำดับ ไม่ซ้ำ และตรวจสอบย้อนหลังได้ ปัญหาคือเจ้าหน้าที่หลายคนบันทึกพร้อมกันได้

วิธีที่ดูง่ายแต่ผิด คือให้แต่ละเครื่องนับจากจำนวนรายการที่มีอยู่แล้วบวกหนึ่ง เพราะถ้าสองคนอ่านค่าเดียวกันในเวลาใกล้กัน ทั้งคู่จะได้เลขเดียวกัน และจะรู้ตัวก็ต่อเมื่อเอกสารออกไปถึงมือลูกค้าแล้ว

ระบบจึงจัดการลำดับเลขที่เอกสารไว้ที่ฝั่งเซิร์ฟเวอร์เป็นชุดข้อมูลของตัวเอง แยกจากตารางรายการ เพื่อให้การขอเลขถัดไปเป็นการทำงานที่ควบคุมลำดับได้จากจุดเดียว

## 4. หนึ่งเอกสาร หลายช่องทางชำระ

ในงานจริง ลูกค้าหนึ่งรายอาจชำระด้วยเงินสดบางส่วน เช็คบางส่วน และโอนบางส่วนในคราวเดียว รวมถึงมีค่าธรรมเนียมแยกต่างหาก

ระบบจึงออกแบบให้เอกสารหนึ่งใบมีรายการชำระได้หลายประเภท แล้ว **ตรวจยอดรวมของทุกช่องทางเทียบกับยอดที่ต้องชำระก่อนบันทึก** พร้อมแจ้งผู้ใช้ว่ายอดยังขาดอยู่เท่าใด แทนการปล่อยให้บันทึกไปก่อนแล้วไปพบความผิดพลาดตอนกระทบยอดสิ้นวัน

ระบบรองรับทั้งการขายสดและขายเชื่อ พร้อมติดตามยอดคงค้างและรายการที่ครบกำหนดชำระ

## 5. หลักฐานของงานภาคสนาม

งานที่เกิดนอกสำนักงานต้องตรวจสอบย้อนหลังได้ ระบบจึงเก็บสองอย่างควบคู่กับรายการ

- **ตำแหน่งขณะบันทึก** โดยขอสิทธิ์เข้าถึงตำแหน่งจากเบราว์เซอร์ และแจ้งผู้ใช้ให้อนุญาตเมื่อถูกปฏิเสธ
- **ไฟล์แนบ** เช่น ภาพสลิปโอนเงินหรือเช็ค ผูกกับรายการนั้นโดยตรง

## 6. สิทธิ์แยกเป็น Role และ Permission

ระบบไม่ผูกสิทธิ์ไว้กับชื่อตำแหน่งในโค้ด แต่แยกเป็นสิทธิ์ย่อยและบทบาท แล้วจับคู่กันในฐานข้อมูล

ข้อดีคือเมื่อองค์กรต้องการเปลี่ยนว่าบทบาทใดทำอะไรได้ ผู้ดูแลปรับได้เองทันที ไม่ต้องรอรอบ Deploy และไม่ต้องแก้โค้ดที่กระจายอยู่หลายจุด

## 7. บทเรียนที่ได้

1. **การนับต่อจากข้อมูลที่มีอยู่ ไม่ใช่การออกเลขลำดับ** ทุกครั้งที่ต้องการเลขที่ไม่ซ้ำในระบบที่มีผู้ใช้พร้อมกัน ต้องมีจุดเดียวที่ควบคุมลำดับ
2. **ตรวจความครบถ้วนของยอดก่อนบันทึก ไม่ใช่ตอนกระทบยอด** ความผิดพลาดเรื่องเงินยิ่งพบช้ายิ่งแก้แพง
3. **การต่อกับระบบเดิมคือการยอมรับข้อจำกัดของคนอื่น** ความสำเร็จของงานลักษณะนี้วัดจากการไม่ไปทำให้ระบบที่ใช้งานอยู่เสียหาย มากกว่าความสวยงามของโครงสร้างใหม่
